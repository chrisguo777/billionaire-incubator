# 经历库人工核对（2026-11-20，开发分支，尚未提交 PR）

## 问题与行为

原解析流程把 AI 整理出的事实全部标为 `user_confirmed`，用户尚未看过结果就得到绿色「已确认」。本次将来源和确认状态分开展示：来自原简历 / 来自追问回答 / 本人修改；尚未核对 / 本人已确认。确认表示本人认可，不表示系统核实事实真实性。

现在流程为：解析简历 → 对照原文核对、修改、删除 → 确认后分析 JD 与匹配 → 追问 → 审阅改写与导出。

- 每条事实可以单独确认，也可在检查后按经历批量确认。保存修改不会自动确认。
- 成果可以分别修改描述、数值、单位、统计口径。空内容不能保存；删除提供一步撤销。
- 姓名、联系方式、教育、单位、职位、日期和经历名称可编辑；这些结构信息采用整体核对勾选，不逐字段新增确认状态。
- 初始核对完成前，前端不发起 JD 匹配，服务端也阻止未核对的 CV / 编辑事实继续下游步骤。
- 追问提取的普通事实和成果均先待核对；新增信息可以按经历确认并更新匹配。生成前还有未核对事实时拦截。
- 重新编辑经历库前，清除旧匹配、当前待答问题和生成结果；保留 DB 及已有问答记录用于再次匹配。修改 / 删除不会自动改写用户上传的原始 CV。
- 沿用已有 Fact / Outcome 的 source、status 字段，没有修改业务 schema 或增加依赖。页面会话版本从 1 升到 2；旧会话不继承自动「已确认」，需重新解析。已保存的新版核对进度可在当前标签页刷新恢复，未保存的编辑草稿不恢复。

## 旧原句回流的处理与取舍

事实和完整原句在现有 schema 中没有逐项对应关系。不能可靠地自动改一条原句中的相应部分。因此修改或删除某条事实时，暂停整个受影响经历的完整原句自动保留（`original_bullets=[]`），也移除同一来源块在其他卡片中的副本。保留空数组，避免旧数据兼容逻辑重新从 CV 导入。

该经历以后使用剩余的已确认事实提出新 bullet，必须逐条接受后才能进入最终稿。未修改经历继续沿用原句保留规则。界面明确提示此取舍，用户可撤销上一步恢复原句。只更改结构信息（如单位或日期）不会清除 bullet 原句。

这不是细粒度的事实到句子溯源，也不保证消除其他事实中重复表达的同一内容；用户仍需逐条核对。新增生成文字依然受现有数字规则限制，完整语义核验尚未实现。
